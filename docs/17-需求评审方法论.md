# 17 - 需求评审方法论（字节测开高频追问点）

> **本文目的**：把"需求评审时能提什么疑问"这件事沉淀成可复用 checklist + MiniMall 实战案例。
> 字节三面聊项目时，**追问最多的问题之一就是"你当时评审时提出了哪些问题"**——本文告诉你怎么答。

---

## 0. 一句话心法

> 评审不是"念一遍 PRD 看有没有错字"，是**用业务 + 技术 + 用户 三视角找盲点**。
> 一次评审能提出 **3~8 个建设性疑问**的人，面试官立即知道这是有项目经验的人。

---

## 1. 评审四问（拿到任何 PRD 都先问这四问）

| # | 提问模板 | 用意 |
|---|---|---|
| ❶ | **业务目标是什么？关键指标是什么？验收怎么量化？** | 防止 PRD 写成"功能清单"——业务方说不清目标就是没想清楚 |
| ❷ | **状态机是什么？所有合法转移 + 非法转移？** | 80% 的并发 bug 来自状态机设计不清楚 |
| ❸ | **谁对谁负责？数据归属？越权策略？** | 防越权、鉴权漏是面试高频追问点 |
| ❹ | **失败兜底是什么？客户端怎么感知？** | 防单边账、防"看上去成功实际失败" |

> 心法：拿到 PRD **先在心里画一张"客户端 → 服务端 → 数据库"的状态转移图**，把"如果网络断了怎么办/用户重复点怎么办/两个人同时付同一单怎么办"主动想一遍——能想出来的就是好需求评审。

---

## 2. 评审 Checklist（10 大类盲点）

按 **PRD 完整度** 排序——前 4 项必查，**任何一项缺失都是 P0**。

### 2.1 数据契约

- [ ] 字段类型/取值范围/默认值
- [ ] 必填 vs 可选
- [ ] 字符长度上限（手机号 11、用户名 3-32、文本框 200）
- [ ] 大小写/前后空格/全角半角处理
- [ ] 时区（全部 UTC，客户端展示时转换）

### 2.2 业务不变量

- [ ] 库存：≥ 0（物理不变量）
- [ ] 价格：≥ 0
- [ ] 优惠券面值：≥ 0 且 ≤ 实际订单金额
- [ ] 订单状态：`UNPAID → PAID/CANCELLED`，`PAID → REFUNDED`（不可逆）
- [ ] 用户名唯一 / 手机号唯一

### 2.3 状态机

- [ ] 当前状态所有合法后继
- [ ] 非法转移如何处理（拒绝 + 业务码）
- [ ] 幂等：同一操作重复执行的结果是否一致
- [ ] 中断恢复：操作中断后从下一状态起恢复，不重做已完成步骤

### 2.4 边界/异常

- [ ] 边界值：恰好 = 门槛、恰好 = 库存上限、首次 / 末次
- [ ] 错误输入：空、Null、超长、特殊字符、Unicode、emoji
- [ ] 并发：相同 key 同账号并发 / 不同账号并发
- [ ] 中途网络断 / 服务降级 / 限流
- [ ] 数据为空时（空购物车、空订单列表）

### 2.5 鉴权 / 越权

- [ ] 是否需要登录（哪些端点）
- [ ] 用户对资源的所有权校验
- [ ] 角色权限（普通用户 vs 管理员 vs 客服）
- [ ] Token 生命周期 / 异地登录 / 多设备互踢
- [ ] 敏感字段脱敏（手机号 138****5678、卡号 BIN）

### 2.6 幂等

- [ ] 创建型操作是否有 Idempotency-Key
- [ ] 支付/退款/打款的回调是否幂等
- [ ] 同一幂等键的服务端存储时长
- [ ] 不同幂等键是否会互相干扰

### 2.7 数据一致性

- [ ] 强一致 vs 最终一致
- [ ] 分布式事务方案（TCC/SAGA/本地消息表）
- [ ] 缓存与 DB 一致（写穿透/失效）
- [ ] 跨服务调用失败时的对账

### 2.8 性能 / 容量

- [ ] 目标 QPS / p95 延迟
- [ ] 关键接口峰值（双 11 / 大促）
- [ ] 数据量上限（用户/订单/优惠券数）
- [ ] 是否需要分库分表 / 异步队列

### 2.9 可观测 / 可运维

- [ ] 关键指标埋点（转化漏斗、错误率）
- [ ] 告警阈值
- [ ] 链路 trace（哪个服务慢）
- [ ] 灰度发布 / 蓝绿 / A-B

### 2.10 兼容性 / 回滚

- [ ] 旧客户端兼容（API 版本管理）
- [ ] 数据迁移方案（schema 变了怎么办）
- [ ] 灰度回滚（开关 / 影子流量）
- [ ] 紧急下线预案（feature flag）

## 3. MiniMall 实战：我评审"优惠券"模块时提的 8 个疑问

> 这是项目里`docs/02-需求评审记录.md`的真实场景化复盘——让你看到 checklist 怎么落地。

| # | 我的疑问 | 风险 | 决策 |
|---|---|---|---|
| 1 | 优惠券面额是否会计入支付金额？退款分摊规则？ | 用户付了 ¥100 用了一张满减券，退款时按什么比例退 | 退款时按实际支付金额退，**券面值不退**（虚拟商品不回退），已在 sprint 决议写明 |
| 2 | 多张券叠加时，叠加规则是按面值累加还是按比例? | 测试与产品理解不一致 → 用户看到"反直觉"的抵扣 | 按 **`stackable=True`** 字段判定，仅支持"先用一主券，其余不叠加"——文档化 |
| 3 | 过期券是否在前端标灰？后端什么时候过期（UTC）？ | 用户看到能领但点了报"已过期"产生客诉 | 前端每 5min 拉一次；后端用 UTC datetime 比较——已在 server 实现 |
| 4 | 取消订单后，已核销券是否自动退回用户口袋？ | 用户误操作取消后想再用券，发现券没了 | 实现 `UserCoupon.used=False` 回退，已被 `test_cancel_returns_coupon` 锁定 |
| 5 | 同一张券并发核销，如何保证只用一个请求能成功？ | 资损：用券抵扣价被并发多次用 | 用 `WHERE used=False` 原子条件更新，失败者拿到业务码 3004"已被使用（并发冲突）" |
| 6 | 总限领 vs 每人限领是否冲突？ | 全平台被一个用户领完导致无活动库存 | 两层都校验，`UserCoupon` 唯一约束 user+coupon，count 校验 total_limit——已在 server 实现 |
| 7 | 优惠券"已领取"是否计入登录态？登出后还能否用？ | 活动期内未登录的券是否失效 | 登录态不影响券状态，过期判定独立 |
| 8 | 优惠券活动期间商品下架/改价，已领券是否仍然有效？ | 改价后券门槛可能不变但用户买到的商品已下架 | 券依据**原价**计算，用户下单时按**当前价**结算——两套定价要分别存 |

这 8 条进评审纪要，谁决策谁定；定下来后每条都有对应自动化用例覆盖（详见 `automation/test_component.py` 内的 `test_coupon_*` 系列）。

## 4. MiniMall 实战：评审"下单 + 支付"模块我提的疑问

| # | 疑问 | 风险 | 决策 |
|---|---|---|---|
| 1 | 下单幂等：客户端弱网重试会重复下单吗？ | 资损（多扣库存、多出钱） | 服务端 `Idempotency-Key` 持久化，同 key 返回同一 order_no |
| 2 | 库存什么时候真正扣？下单时 / 支付时？ | "超卖"问题——超额成交 | **下单时**原子扣（`UPDATE WHERE stock>=qty`），如失败整单回滚 |
| 3 | 第三方支付失败但已经扣款（单边账）怎么处理？ | 用户付了款但订单仍"待支付" | 服务端主动轮询 + 用户端在 30s 内未明确状态时跳"订单详情"轮询（mitmproxy 抓包断言） |
| 4 | 支付回调可以重复接收吗？是否要去重？ | 同一笔订单支付重复成功 → 多发货/多发券 | 服务端去重，幂等表记录——已被 `test_pay_idempotent_no_double_charge` 覆盖 |
| 5 | 取消订单的窗口期？ | 用户点完支付后立即点取消 | UNPAID 可取消；PAID 只能退款；状态码 4004 "仅待支付订单可取消" |
| 6 | 退款成功后，库存是否回滚？ | 用户退款后系统库存错乱 | 业务决策"虚拟商品退款不回库存"，**写在 PRD + docs/14** |
| 7 | 价格改后老订单金额冻结？ | 用户客服投诉"改价我订单变了" | `OrderItem.price` 下单时冻结，写入数据库 |
| 8 | 用户 A 拿用户 B 的订单号能支付吗？ | 越权 | 服务端校验 `order.user_id == auth_uid()`，业务码 4002 |

## 5. 评审争议的解决姿势

| 场景 | 怎么应对 |
|---|---|
| 开发说"这个用例不用测" | "麻烦给我 SLA——经手这个函数的是测试；如果是产品/业务决策，请进 PRD 写明不测。否则视为需测" |
| PM 说"用户不会这么用" | "上次 BUG-001 就是用户加购 0 件测试复现的——异常态不一定是 main case，但**会出 case**" |
| "上线后再说" | "上线后修的成本是开发期 ×5~×10，能否给我至少 blocking1 优先级在 sprint backlog？" |
| "我们已经做过了" | "能看到 README/代码/接口文档哪一处说明这个已经有边界保护吗？"——**拿出证据** |

## 6. 三面考"你做过哪些有影响力的评审动作"——答题模板

> "我习惯拿 PRD 第一时间画**状态机 + 数据契约**两张图。在 MiniMall 优惠券评审时，我提了 8 条业务疑问，最有价值的 3 条是：
>
> ① **退款分摊**：用券订单退款时实际支付金额退给用户、券面值不退——这条不在原 PRD 里，是我和产品+开发反复沟通后落地的业务定义，避免了上线后的客诉与退款超付；
>
> ② **状态机/转移**：让 PM 写明所有合法+非法的订单状态转移，作为后续测试的依据（不能边开发边补）；
>
> ③ **并发核销**：券不能被多个请求并发核销——这条在写代码之前我已建议用 `WHERE used=False` 原子条件，开发落地后并发测试通过。
>
> 这 3 条都已被对应的自动化用例锁定（见 `automation/test_integration.py`），任何后续修改都会被 CI 卡住。"

## 8. 复述：需求评审 = 把"未定义"暴露出来

> 关键不是"评审时找不找得到 bug"——是**让 PM 和开发把规则写明**。
> 写明了，**测试才能测；不写明，上线后客诉才会暴露**——成本差 5 倍起。
>
> 这是字节最看重的"业务思维"：**不是为了挑刺，是为了把规则沉淀下来**。
