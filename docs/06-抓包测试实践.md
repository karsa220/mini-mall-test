# 抓包测试实践（Charles）

> 对应 JD"熟练使用 Charles/Fiddler"。本文档记录本项目弱网专项与安全检查中 Charles 的实际用法。

## 1. 抓包配置

- 被测服务为本地 HTTP（127.0.0.1:5000），无需 HTTPS 证书；模拟 App 真机场景时按"手机代理到电脑 IP:8888 + chls.pro/ssl 装证书"配置。
- Proxy → Recording Settings → Include 只录 `127.0.0.1:5000`，过滤噪音。

## 2. 弱网模拟（Throttle）

Proxy → Throttle Settings → Enable Throttling：

| 场景 | 带宽 | 延迟 | 验证点 |
|---|---|---|---|
| 3G | 400 kbps | 300ms | 下单接口超时提示是否合理、前端有无 loading |
| 极差网络 | 100 kbps | 2000ms + 10% 丢包 | 超时后重试是否产生重复订单（验证幂等） |

**发现**：弱网下客户端超时重试场景下，若首次下单成功但响应未及时返回、客户端重试同一下单请求，当前实现依赖"清空购物车"兜底——重试时购物车已空返回 3001，未生成多笔；但该兜底非标准幂等设计，应在 server 端补 requestId 去重以彻底闭环（BUG-003 待修复项）。

## 3. 断点改包（Breakpoints）——服务端校验测试

对 `/api/order/create` 打断点，拦截请求后修改：

| 篡改项 | 目的 | 结果 |
|---|---|---|
| coupon_code 改为不存在的码 | 服务端是否校验券合法性 | 被拦截（合格） |
| 拦截响应，把 payable 改小再发给客户端 | 验证客户端是否盲信响应 | 仅展示问题，金额以服务端为准（合格） |

## 4. 并发重放（Repeat Advanced）——幂等验证

对 `/api/order/create` 右键 Repeat Advanced 并发重放同一请求。

- **代码层面**：下单接口无幂等令牌（requestId/clientToken）去重，每次请求都新建 order_id 并写入 ORDERS（server.py 第 156 行标注 BUG-003）。
- **实测对照（验证脚本 `automation/verify_idempotency_parallel.py`）**：
  - *单进程串行（无延迟）*：首个请求成功后即清空购物车（第 165 行），GIL 串行下其余并发请求读到空购物车返回 3001，**实测 8 并发仅生成 1 笔**——"清空购物车"在此场景下意外成了弱兜底，掩盖了缺陷。
  - *并行后端 + 真实延迟（模拟 DB/下游耗时，等价于 Charles Throttle 弱网下客户端并发重试）*：用 `threaded=True` 多线 worker 并注入 0.3s 延迟放大"读购物车→清购物车"竞态窗口，**实测 8 并发生成 8 笔订单**（8 个去重 order_id），重复下单确凿复现。
- **风险定性**：缺陷真实存在，仅在单进程串行开发服务器下被兜底掩盖；迁移到并行/异步后端或弱网重试场景必现。下单接口应补 requestId 去重，属真实待修复缺陷（BUG-003）。

## 5. Map Local —— Mock 难构造场景

将 `/api/cart` 响应映射到本地 JSON，构造"购物车含已下架商品""金额为超大数"等后端难以快速造出的场景，验证前端/下游逻辑容错。

## 6. 安全检查清单（抓包确认）

| 检查项 | 方法 | 结论 |
|---|---|---|
| token 是否出现在 URL | 抓包看请求行 | 否，走 Header（合格） |
| 密码是否明文传输 | 看 /api/login 请求体 | 本地 HTTP 明文 → 生产必须 HTTPS，列为遗留风险 |
| 越权 | 用 test01 的 token 抓包改 order_id 为 test02 的订单 | 被 4002 拦截（合格，对应 ORD-05） |

## 7. mitmproxy 脚本化抓包（进阶：可进 CI 的抓包自动化）

Charles 是 GUI 手工工具，无法写断言、跑不了 CI。测开的价值在自动化，因此本项目额外用 mitmproxy 把抓包做成可重复、可断言、可落盘的工程能力：

- `automation/mitmproxy_addon.py`：Python 写 addon，代理 MiniMall 流量时自动对登录/下单/支付请求与响应做字段断言（请求含 username/password、响应返回 token/order_id/已支付状态），并实时导出标准 HAR（`capture.har`）与断言汇总（`mitm_assertions.json`）。
- `automation/run_mitm_capture.py`：单命令自包含（释放端口 → 起 server → 起 mitmdump 代理 → 跑业务流 → 读断言），退出码反映断言是否全通过，**可直接接进 pytest / CI**。
- **实测**：`python automation/run_mitm_capture.py` 退出码 0，5 条断言全 PASS（登录请求/响应、下单请求/响应、支付响应），HAR 与断言 JSON 均落盘。

> 价值：Charles 证明"我会用工具、有证据"；mitmproxy 证明"我把抓包做成可重复的自动化资产"——这正是测开与手工测试的分水岭，也是 JD"熟练 Charles/Fiddler"之上更硬的加分项。

## 8. mitmproxy 改包 / Mock 响应（测开抓包核心：伪造异常场景）

Charles 的 Breakpoints（改请求）/ Map Local（伪造响应）在 mitmproxy 里写成脚本，可进 CI、可断言：

- **request 钩子改包**（等价 Charles Breakpoints 拦截请求）：把 `/api/order/create` 的优惠券改成无效码，验证服务端是否真的校验券合法性（脏数据注入测试）。
- **response 钩子 Mock**（等价 Charles Map Local 伪造响应）：把 `/api/order/pay` 改成 `504 支付网关超时`，构造弱网 / 支付通道故障场景，验证客户端与下游容错。
- 落地：`automation/mitmproxy_mock_addon.py` + `automation/run_mock_capture.py`，退出码反映 mock 是否生效，事件落盘 `mitm_mock_events.json`。
- **实测**：支付请求被代理拦截并返回 504，事件成功记录。

> **关于 HTTPS / SSL Pinning 绕过——本项目不做、也不需要**。理由：Pinning 绕过（Frida / Objection hook 客户端 `checkServerTrusted` / `SSLContext`）针对的是"你不掌控证书、需强行让代理被信任"的场景，即第三方 App、竞品或授权渗透测试，涉及逆向与 root，已越过"正常测试"边界。对**自有 / 公司产品**测试，测试环境本就能直接安装代理证书、或测试包直接关闭 Pinning，正常配 Charles / mitmproxy 即可。因此本模块只保留"测试环境语境下的改包 / Mock"这一日常刚需能力，不把逆向绕过写进实战。

## 9. WebSocket 抓包

App 实时消息通道（如订单状态推送）也要抓。服务端用独立 `websockets` 库在 **5001 端口**推送订单状态：下单后广播 `order_created`、支付后广播 `order_paid`（见 `app/server.py`，早期试过 `flask_sock` 绑定 5000，但与 Werkzeug 3.1.8 不兼容，故改为独立端口方案）。

- mitmproxy 拦截 WS 流量（`websocket_message` 钩子），记录每条消息方向，并对服务端推送的 `order_created` / `order_paid` 做断言：**必须携带 order_id**。
- 落地：`automation/mitmproxy_ws_addon.py` + `automation/run_ws_capture.py`。
- **实测**：抓到 `subscribe` / `order_created` / `order_paid` 三条消息，两条推送断言均含 order_id 且 PASS。

## 10. HAR 契约 diff（接口变更回归）

把抓包产物 `capture.har` 当成"接口契约快照"，防止后端偷偷改接口：

- 首次运行抽取每个 `/api` 路由的响应字段结构（字段名 + 类型），生成基线 `contract_baseline.json`；
- 后续运行与基线对比，报告**新增字段 / 删除字段 / 类型变化**；删除字段、类型变化 = breaking change（退出码 1），新增字段仅警告（退出码 0）。
- 落地：`automation/har_contract_diff.py`。
- **价值**：后端把 `order_id` 改名或 `price` 由 number 变 string，抓包 diff 立刻报警，比人工比对 HAR 高效。

## 11. 四个能力已接 pytest + Jenkins CI

- `automation/test_mitm_capture.py`：4 个用例（基础字段断言 / WebSocket 抓包 / Mock改包 / HAR 契约 diff），**实跑全 PASSED**。
- 根目录 `Jenkinsfile` 新增 stage「抓包自动化 (mitmproxy)」：`python3 -m pytest test_mitm_capture.py -v`，退出码即断言结果，可直接作为质量门禁。
- 至此"抓包"形成完整闭环：**Charles 手工证据 → mitmproxy 可重复自动化资产 → pytest 可断言 → Jenkins CI 门禁**。
