# 抓包测试实践（Charles）

> 对应 JD"熟练使用 Charles/Fiddler"。本文档记录本项目弱网专项与安全检查中 Charles 的实际用法。

## 1. 抓包配置

- 被测服务为本地 HTTP（127.0.0.1:5000），无需 HTTPS 证书；模拟 App 真机场景时按"手机代理到电脑 IP:8888 + chls.pro/ssl 装证书"配置。
- Proxy → Recording Settings → Include 只录 `127.0.0.1:5000`，过滤噪音。

## 2. 弱网模拟（Throttle）

Proxy → Throttle Settings → Enable Throttling：

| 场景 | 带宽 | 延迟 | 验证点 |
|---|---|---|---|
| 3G | 400 kbps | 300ms | 下单接口超时提示是否合理、前端有无 loading |
| 极差网络 | 100 kbps | 2000ms + 10% 丢包 | 超时后重试是否产生重复订单（验证幂等） |

**发现**：弱网下客户端超时重试会直接触发重复下单（BUG-003 的真实触发路径），说明幂等缺陷在弱网环境下必然暴露，提升了该缺陷的严重级别（一般 → 严重）。

## 3. 断点改包（Breakpoints）——服务端校验测试

对 `/api/order/create` 打断点，拦截请求后修改：

| 篡改项 | 目的 | 结果 |
|---|---|---|
| coupon_code 改为不存在的码 | 服务端是否校验券合法性 | 被拦截（合格） |
| 拦截响应，把 payable 改小再发给客户端 | 验证客户端是否盲信响应 | 仅展示问题，金额以服务端为准（合格） |

## 4. 并发重放（Repeat Advanced）——幂等验证

对 `/api/order/create` 右键 Repeat Advanced：并发 5 次。

- 预期：只生成 1 笔订单
- 实际：**生成 5 笔订单**，坐实 BUG-003，并提供复现证据（截图 + 订单列表对比）

## 5. Map Local —— Mock 难构造场景

将 `/api/cart` 响应映射到本地 JSON，构造"购物车含已下架商品""金额为超大数"等后端难以快速造出的场景，验证前端/下游逻辑容错。

## 6. 安全检查清单（抓包确认）

| 检查项 | 方法 | 结论 |
|---|---|---|
| token 是否出现在 URL | 抓包看请求行 | 否，走 Header（合格） |
| 密码是否明文传输 | 看 /api/login 请求体 | 本地 HTTP 明文 → 生产必须 HTTPS，列为遗留风险 |
| 越权 | 用 test01 的 token 抓包改 order_id 为 test02 的订单 | 被 4002 拦截（合格，对应 ORD-05） |
