# 16 - 业务思维：订单 / 支付 / 优惠券模块端到端测试方案

> **本文目的**：把 MiniMall 项目里"业务测试思维"沉淀成可复用的方法论，对标字节测开二面"业务方案题"的回答模板。
> 面试时被问到"订单/支付/优惠券模块怎么设计测试方案"，按本文骨架回答即可（结构 → 维度 → 用例 → 优先级 → 自动化分层）。

---

## 0. 一句话立骨架（先说骨架再说细节）

> 这个模块的业务复杂度在**资金 + 状态 + 促销 + 高并发**四个交叉点上。我会按"端到端 + 分层"两条主线展开：
>
> - **端到端**：从用户决策（看商品→领券→加购→下单）→ 资金流转（下单扣库存→支付→退/退款）→ 状态一致（订单/优惠券/库存三方对齐）→ 观测（metrics/HAR 契约守护）。
> - **分层**：单元（促销引擎/库存纯逻辑）→ 组件（Flask test_client 覆盖全部端点正负）→ 集成（端到端+幂等重试）→ 并发竞态（防超卖、防重复核销）→ 安全（越权/篡改/注入/爆破）→ 性能（Locust 压测）→ 混沌（应用级+网络级）。

面试官听到这个开篇，对你的"全局视角"已经心里有数。

## 1. 数据层（先讲清楚数据从哪来）

| 数据源 | 字段 | 业务约束 | 用例侧验证点 |
|---|---|---|---|
| `Product` | id/name/category/price/stock/status | 上架=1 才能展示/购买；stock≥0 物理不变量 | 价格非法（0/负/NaN/字符串）、库存为 0、价格篡改（mitmproxy 改包） |
| `Coupon` | code/type/threshold/value/rate/cap/category/stackable/per_user_limit/total_limit/end_at | type 决定促销引擎分支；end_at 是 UTC datetime | 有效期内/已过期/未生效；总限领、每人限领 |
| `UserCoupon` | user_id/coupon_id/used | user_id+coupon_id 唯一；used=False 可核销 | 同一券被并发领取/核销 |
| `Order` | order_no/user_id/status/total/discount/payable/coupon_id/idem_key | status 状态机：`UNPAID → PAID`；`→ CANCELLED` 或 `→ REFUNDED`（不可逆） | 状态机所有合法+非法转移 |
| `OrderItem` | order_id/product_id/qty/price | 下单时**冻结价格**（防商品改价影响历史订单） | 改商品价格后历史订单金额不变 |
| `Idempotency` | key/order_no | 同 key 重试返回同一 order_no，不重复下单/扣款 | 弱网重复创建同 key 不出现多笔订单 |
| `CartItem` | user_id/product_id/qty | user_id+product_id 唯一；qty 与库存上下界 | qty=0/负数入购物车（边界——已埋 BUG-001） |
| `Address` | name/phone/detail | name+phone+detail 三段全必填；归属当前用户 | 删他人地址、phone 格式、姓名长度 |

**这一层的关键设计评审点**：
- 订单用 `order_no`（业务号，UUID 时间戳 + 随机 4 位）而非 DB 自增 id，外部接口防枚举
- 下单时冻结价格（写入 OrderItem.price），不依赖商品当前价，**抗改价**
- `Idempotency` 表是幂等键落库的位置，要持久化（不只内存），进程重启不丢幂等

## 2. 接口层（参数 + 响应 + 下游）

逐端点列**契约 + 测试维度**（不是"测一下"，是"测什么 + 为什么"）：

### 2.1 下单 `/api/order/create` POST

| 参数 | 测试维度 | 验证点 | 对应实现 / 用例 |
|---|---|---|---|
| `coupon_code`（可选） | 类型/缺失/不存在/未领取/已使用 | 业务码 3004 | `test_coupon_unowned_or_used`，`test_concurrent_coupon_redemption_rejected` |
| 头 `Idempotency-Key`（可选） | 缺/同 key 重试/不同 key | 重复 key 返回同一 order_no | `test_idempotency_same_key_returns_existing_order` |
| 库存（下单时校验） | 超库存 | 业务码 2003 | `test_insufficient_stock_blocked` + 并发 `test_concurrent_orders_cannot_oversell` |
| 登录态 | 缺/错/已吊销 token | 业务码 401 | `test_order_endpoints_require_auth` |
| 购物车空 | - | 业务码 3001 | `test_empty_cart_blocked` |

**响应字段含义（必须测的形状变化）**：
- `data.order_id` / `order_no` 同值（双字段是为了兼容老旧客户端）
- `data.status` 必定是 `UNPAID`，**严禁直接返回 PAID**——曾有过逻辑 bug 让客户端以为可立即发货
- `data.discount` 只在用了券时 > 0；用券失败回滚时**整单不创建**

### 2.2 支付 `/api/order/pay` POST

| 状态转移 | 测试维度 | 业务码 | 验证 |
|---|---|---|---|
| `UNPAID → PAID` | 首次支付 | 0 | 默认态 |
| `PAID → PAID` 重复支付 | 同 order_no 重试 | 0（幂等，**不允许错误**） | `test_pay_idempotent_no_double_charge` |
| `UNPAID → CANCELLED` | 取消订单 | 0 | `test_cancel_unpaid` |
| `CANCELLED → PAID` | 取消后再付 | 4003 | `test_cancel_then_pay_blocked` |
| `UNPAID → REFUNDED` | 直接退款 | 4005 | `test_refund_unpaid_blocked` |
| 他人订单 | 越权访问 | 4002 | `test_cannot_pay_others_order` |
| 不存在的 order_no | - | 4001 | `test_pay_unknown_order` |

**回调/补单（在生产环境是支付平台回调；在 MiniMall 我们直接同步支付）**：
- 即便没有回调，**也必须有客户端主动查询的对账能力**——这是单边账防护（面经高频问"支付成功但回调失败怎么办"）
- 对应的端点是 `GET /api/orders/<order_id>`，客户端应该在 30s 内仍未确定时轮询

### 2.3 退款 `/api/order/<id>/refund` POST

| 状态 | 测试点 |
|---|---|
| `PAID → REFUNDED` | 正常路径 |
| `UNPAID → REFUNDED` | 业务码 4005（必须先付再退） |
| `REFUNDED → REFUNDED` 重复退款 | 业务码 4005（已退过） |
| 他人订单 | 业务码 4002（**必须服务端校验**） |
| 不存在的订单 | 业务码 4001 |
| 退款后库存是否回滚？ | **这是个常见设计盲点**：本项目退款不回滚库存（业务定义是"虚拟商品退回即作废"）——但**必须在用例里写明并验证**，让产品/开发确认 |

### 2.4 优惠券（领取/使用/叠加）

业务高频题（面经原话："给你一张满 100 减 10 的优惠券、有效期 3 天、仅食品类，怎么测"）

| 维度 | 用例 | 验证 |
|---|---|---|
| **基础规则** | code 存在/不存在/已过期/未生效 | 6001/6002 |
| **门槛边界** | 恰好等于门槛、低于门槛 0.01、高于门槛 1 分 | 0/3002/0（BUG-002：恰等于门槛被拒） |
| **品类限制** | 食品+非食品混合下单，仅食品金额计入门槛 | 0；非食品满额不算 |
| **每人限领** | 第 N+1 次领取 | 6004 |
| **总数限领** | 第 N+1 次领取 | 6003 |
| **叠加（stackable=true）** | 多张叠加抵扣、按预期顺序生效 | 0；总额不超 |
| **时间维度** | 有效期前 1s、过期后 1s、跨时区 | 时间用 UTC，避免时区歧义 |
| **未用取消订单** | 订单取消后券是否退回 | **回退 used=False**（已实现） |
| **支付超时** | 订单超时未付、券是否释放 | 见 inventory + 时序任务 |
| **退款分摊** | 用券订单退款，券面额是否按比例退回 | 这是字节高频追问点：**退款时按支付金额比例退回券面值** |

## 3. 客户端状态管理（弱网/loading/前后台/缓存）

> 这块是字节考"端到端"特别爱挖的——后端测试工程师常常漏掉。

| 场景 | 期望行为 | 验证手段 |
|---|---|---|
| 弱网下点"创建订单"按钮 | 防重复点击（按钮 disabled + 防抖） | UI 自动化 `test_appium_*` |
| 下单→支付断网 30s 后恢复 | 主动轮询订单状态，不靠回调 | 单测 + 模拟断网（mitmproxy `ChaosProxy`） |
| 切到后台再回来 | 购物车/订单列表从服务端拉取最新，**不依赖本地缓存** | UI 自动化前后台切换 |
| 支付成功页面 loading 卡死 | 有超时跳转兜底 | UI 自动化 + 监控 |
| 本地缓存与服务端不一致（商品改价） | 每次下单必须调用 `/api/products/<id>` 拿当前价（**不能缓存优惠结果**） | 抓包断言（mitmproxy） |

**为什么这条重要**：
- 后端处理幂等是"兜底"
- 前端处理防重复点击是"主动避免"
- **必须双层都有**——面试官追问"前端怎么做、后端怎么做、为什么这么分"

## 4. 业务功能维度——每个交互点独立用例集

## 8. 用例优先级——"只能跑 10 条用例"怎么选

字节常追问的"颗粒度"问题。**优先级判定三原则**：

1. **资损 > 安全 > 主流程 > 边缘文案**
2. **新功能 > 旧代码**
3. **代码触碰过 > 稳定**

### MiniMall 订单/支付模块 Top 10 用例（仅时间紧迫时跑）

| # | 用例 | 维度 | 为什么 |
|---|---|---|---|
| 1 | 主流程：登录→加购→下单→支付→订单状态=PAID | E2E 闭环 | 演示价值 |
| 2 | BUG-001：加购 quantity=0 应被拒 | 边界值 | 复现预埋缺陷 |
| 3 | BUG-002：订单金额恰等于券门槛可用 | 边界值 | 复现预埋缺陷 |

## 9. 自动化分层与 CI 卡口

```
                 ┌──────────────┐
                 │   UI / 移动   │  Appium 真机，回归用
                 └──────┬───────┘
                        │
                 ┌──────┴───────┐
                 │   集成 / 并发 │  test_integration（幂等/超卖/重复核销）
                 └──────┬───────┘
                        │
                 ┌──────┴───────┐
                 │   组件 / 接口 │  test_component（Flask test_client 全端点正负）  ──→  --cov-fail-under=80%
                 └──────┬───────┘
                        │
                 ┌──────┴───────┐
                 │   单元 / 引擎 │  test_unit（促销引擎等价类+边界）  ──→  promotion.py 91% 覆盖
                 └──────────────┘

门禁：Jenkins 并行四 stage；任一不过 fail fast；SonarQube + /metrics 周报
```

- **单元层**：促销引擎边界等价类，跑得最快，覆盖最高
- **组件层**：用 `app.test_client()` 进程内驱动，全部 22 端点正负边界 + BUG 复现
- **集成层**：跨多接口链路 + 并发线程池
- **UI 层**：Appium 真机 + H5，覆盖端到端真实链路

**性能 + 混沌 + 契约**作为门禁外置 stage（每次 PR 跑一次，门禁阈值不达不让合入）。

## 11. 回到需求评审——这几个盲点不进评审会没人提

字节特别看"能不能找到遗漏的边界"。**评审 MiniMall 订单/支付模块时我应该提的疑问**：

1. **下单时价格谁说了算？** 商品改价后老订单金额是否冻结？（我们冻结了，但很多项目不冻结）
2. **支付成功的判定？** 等第三方回调 / 主动轮询 / 客户端确认？如果都不上线，怎么对账？
3. **库存回滚？** 取消/退款后库存是否回？按比例回？还是整单回？（本项目"取消回滚、退款不回"，必须文档化业务定义）
4. **优惠券叠加规则？** 同一订单能否多张叠加？叠加时是按面值累加还是按比例抵扣？（我们用 `stackable` 字段表达，但实际生效规则要评审明确）
5. **退款分摊？** 用券订单退款时，实际支付的金额退给用户，但"券面值"是按比例退还是按金额退？（这是金融侧关注点，业务常漏）
6. **幂等键生命周期？** 客户端 SDK 重试用同 key，服务端要保存多久？24h？订单生命周期？永久？（明确存到 Order.idem_key，本项目持久化到 Idempotency 表）
7. **超时未支付？** 多少分钟后自动取消？是否触发库存回滚？优惠券是否退回？
8. **数据隔离？** 多用户隔离、单用户多端登录、订单归属校验——这些必须有服务端主键校验，不能靠前端隐藏按钮

这 8 条要写在评审纪要里，谁决策就用谁的方案落库 + 用例覆盖。

## 13. 自检：这套方案能扛住的追问

- **"如果用户量翻 100 倍这套方案还能用吗？"**
  → 单元/组件用 test_client 不起进程，并发测试用线程池；Locust 已经在测并发；超卖的 SQL `UPDATE WHERE stock>=qty` 是单语句原子，加索引即可；瓶颈在 `/api/order/create` 是写密集，未来要拆读写 + 异步队列（已写进 docs/14 进阶路线）
- **"如果线上崩溃怎么定位？"**
  → `/metrics` 端点暴露 QPS/错误率/时延分位；WS 推送订单事件做实时审计；mitmproxy 抓包脚本可重放故障时刻的请求；HAR diff 自动告警破坏性变更
- **"测试覆盖率 80%，漏的那 20% 怎么办？"**
  → 覆盖率是必要不充分；剩余是字符解析/容错分支（schema 校验失败时的兜底）和被弃用的代码路径，每漏一处都要进 issue list
- **"这套方案缺点是什么？"**
  → ① 流量回放没有（生产环境流量无法用脚本回放）② 精准测试没有（变更→用例推荐）③ LLM 评测没有（动态数据生成）；都列在 docs/14 进阶路线

## 14. 复述：业务思维的可迁移方法论

> 这套方案的**核心不是"订单怎么测"，是"拿到任何业务模块，怎么拆出 8 维度、30+ 条用例、5 层自动化"**。
>
> 用以下 4 步可拆任何模块：
> 1. 先画**数据流图**（数据从哪来、字段约束、状态机）——找到业务不变量
> 2. 列**接口契约表**（每条路由的参数/响应/业务码）——找到所有边界
> 3. 补**用户旅程**（弱网/前后台/重复点击/缓存一致性）——找到后端常漏的"前端假设"
> 4. **安全 + 性能 + 兼容 + 状态机**——四条线必跑（业务/安全双重保护）
>
> 这 4 步做完，任何模块都能拿到至少 30 条带优先级的用例 + 分层自动化 = 字节二面的标准答案。
