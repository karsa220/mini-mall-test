# MiniMall 企业级测试体系设计

> 目标：把一个"个人测开 demo"升级为能对标字节/大厂测开 JD 的**企业级质量工程**。
> 配套：字节 JD 与面经对标见 `docs/15-字节测开-JD与面经.md`；抓包实践见 `docs/06`。

---

## 1. 分层测试金字塔（核心方法论）

```
        ▲ 少量但关键
       /|\
      / | \         E2E / 真机 UI（Appium）—— 6 用例，交易主链路冒烟
     /  |  \        WebSocket 抓包断言（订单推送）
    /------- \
   /  集成层  \      接口自动化（pytest+requests）—— 21 用例，主体回归
  /  Flask test  \   组件层（test client 进程内）—— 快速校验路由+覆盖率
 /---------------\
/   单元层（底座）\    纯函数单测（calc_amount/造数/边界）—— 最快最稳最便宜
 \---------------/     占比应最大（金字塔底座）
```

原则：**能写低一层的测试就写低一层**。E2E 只保留业务关键链路冒烟，不靠它当安全网。

## 2. 持续测试流水线（CI 门禁，fail fast）

提交即触发，分层门禁任一不过则构建失败：

| 门禁 | 工具 | 阈值/规则 | 不过的后果 |
|---|---|---|---|
| 静态扫描 | SonarQube | 无新增 Blocker 漏洞 | 拦截合入 |
| 单元+组件 | pytest + coverage | `app` 行覆盖 ≥ 60%（随单测增长再提高） | 拦截 |
| 接口自动化 | pytest+requests+YAML | 17 passed + 4 xfail（已知缺陷可重复覆盖） | 拦截 |
| 抓包断言 | mitmproxy | 关键字段断言全 PASS | 拦截 |
| **性能门禁** | **Locust** | **p95 ≤ 800ms、错误率 ≤ 1%** | 拦截（等价于 k6 thresholds） |
| **混沌/容错** | **/api/chaos + mitmproxy** | **故障被系统感知/处理** | 拦截 |
| **契约 diff** | **HAR 契约 diff** | **无破坏性字段变更** | 拦截 |
| 质量度量 | /metrics | QPS/错误率/时延分位归档 | 入仪表盘 |

> 对应 Jenkinsfile 的 `企业级质量门禁` 并行 stage + `质量度量归档` stage。

## 3. 各企业级能力说明（面试题材）

### 3.1 性能测试（JD 点名 Locust；面经高频"关注哪些参数/瓶颈分析"）
- **关注指标**：吞吐（RPS）、响应时间分位数（P50/P95/P99，而非平均）、错误率、资源（CPU/内存/连接数）
- **门禁**：`run_perf_check.py` 解析 Locust 聚合统计，p95 与错误率不达标即非零退出 → CI 失败
- **瓶颈分析思路**：先定位是 CPU 密集 / IO 等待 / 锁竞争 / 外部依赖；本 demo 用 `ORDER_SIM_LATENCY` 放大下单竞态窗口，模拟弱网下客户端重试
- **容量规划**：逐步加压（user 数从 20→200）观察 p95 拐点，得到单实例容量

### 3.2 混沌工程 / 高可用测试（面经"如何模拟异常/支付失败原因"）
- **应用级**：`server.py` 的 `/api/chaos` 注入宕机(503)/随机错误(500)/延迟
- **网络级**：`mitmproxy_chaos_addon.py` 对支付接口注入 504（网关超时）
- **价值**：验证系统**优雅降级**而非静默成功；暴露**幂等缺口**——支付 504 时客户端重试会复现 BUG-003 重复下单，证明"支付失败 ≠ 订单未创建"，必须靠**幂等令牌**兜底

### 3.3 测试数据管理 / 造数（面经"数据污染/造数工具局限性"）
- **合成数据优先于脱敏生产数据**：合规、可重复、可版本化（`data_factory.py`）
- **隔离**：每个用例拿独立命名空间（`DataFactory`），避免 A 用例订单影响 B 用例断言
- **覆盖**：合法 / 边界 / 异常三类，直接喂接口自动化（含 BUG-001/002 边界）

### 3.4 契约测试（面经"依赖第三方接口如何处理"）
- 自研轻量等价物：抓包生成 HAR → 提取各路由响应字段 schema → 存 baseline → 每次 diff
- 新增/删除字段、类型变化自动报警（破坏性变更退出码非 0）= 消费者驱动契约思想

### 3.5 可观测性 / 质量度量（行业共识）
- `server.py` 暴露 `/metrics`：请求总量、5xx 错误数、平均/最大时延
- 与 Prometheus/Grafana/ELK 对接即质量仪表盘；指标：缺陷逃逸率、构建成功率、覆盖率、p95

## 5. 面试话术（如何讲这个项目对标字节）

- **"你的自动化框架怎么做的？"** → 分层金字塔 + pytest 数据驱动 + 自包含起停；不是堆脚本，而是有质量门禁的体系
- **"性能测试关注哪些参数？"** → RPS/P95/P99/错误率，门禁卡 p95 与错误率，按加压拐点做容量规划
- **"如何模拟异常？"** → 应用级 /api/chaos + 网络级 mitmproxy 504，验证降级与幂等缺口
- **"数据污染怎么解决？"** → 合成数据工厂 + 每用例独立命名空间
- **"最值得的 Bug？"** → BUG-003：并行后端+弱网下 8 并发复现 8 笔重复订单，推动幂等令牌方案
- **"为什么造这个体系？"** → 把"会写用例"升级为"质量赋能"：抓包/性能/混沌/契约全部自动化且进 CI，fail fast
