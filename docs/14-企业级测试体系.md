# MiniMall 企业级测试体系设计

> 目标：把一个"个人测开 demo"升级为能对标字节/大厂测开 JD 的**企业级质量工程**。
> 本次核心变化：被测系统从"内存字典玩具"重构为**真实关系型电商后端**（SQLAlchemy + SQLite，22 端点），测试升级为**四层测试金字塔 + 三项企业级门禁**，覆盖率 89%。
> 配套：字节 JD 与面经对标见 `docs/15-字节测开-JD与面经.md`；抓包实践见 `docs/06`。

---

## 1. 被测系统（真实业务后端）

| 领域 | 端点 | 关键能力 |
|---|---|---|
| 用户/鉴权 | /api/register /login /logout /profile | 密码哈希 + 签名 Bearer token + 登出吊销 + 登录限流 |
| 收货地址 | /api/addresses (POST/GET/DELETE) | 归属校验（越权拒绝） |
| 商品 | /api/products(搜索/分类/排序/分页) + 管理端新增/调库存 | 参数化查询防注入 |
| 优惠券 | 领取/我的券/管理端发放 | 满减/折扣/品类/叠加/有效期/限领 |
| 购物车 | 增/查/改/删/清 | 归属隔离 |
| 订单 | 创建/支付/取消/退款/列表/详情 | 幂等、原子扣库存、优惠券原子核销 |
| 可观测/韧性 | /metrics + /api/chaos/* | 指标采集 + 故障注入 |

> 数据模型见 `app/db.py`；营销规则引擎见 `app/promotion.py`（纯函数，可单测）。

## 2. 分层测试金字塔（核心方法论）

```
        ▲ 少量但关键
       /|\
      / | \         E2E / 真机 UI（Appium）—— 交易主链路冒烟
     /  |  \        企业级门禁（性能/混沌/契约）—— 3 项
    /------- \
   / 集成层   \      交易一致性（幂等/并发防超卖/防重复核销）—— 6 例
  /  组件层    \     全端点正负边界（Flask test client）—— 39 例
 /  安全专项    \    越权/注入/限流 —— 8 例
/  单元层(底座) \    促销引擎纯函数 —— 15 例（占比最大、最快最稳）
 \---------------/
```

原则：**能写低一层的测试就写低一层**。E2E 只保留业务关键链路冒烟，不靠它当安全网。

## 3. 持续测试流水线（CI 门禁，fail fast）

| 门禁 | 工具 | 阈值/规则 | 不过的后果 |
|---|---|---|---|
| 单元+组件+集成+安全 | pytest + coverage | `server/db/promotion` 行覆盖 ≥ 80%（当前 89%） | 拦截 |
| 接口自动化 | 四层测试（进程内 test_client） | 73 passed | 拦截 |
| 抓包断言 | mitmproxy | 关键字段断言全 PASS | 拦截 |
| **性能门禁** | **Locust** | **p95 ≤ 800ms、错误率 ≤ 1%** | 拦截（等价 k6 thresholds） |
| **混沌/容错** | **/api/chaos + mitmproxy** | **故障被感知/降级 + 幂等重试不重复** | 拦截 |
| **契约 diff** | **HAR 契约 diff** | **无破坏性字段变更** | 拦截 |
| 质量度量 | /metrics | QPS/错误率/时延归档 | 入仪表盘 |

> 对应 `Jenkinsfile` 的四层并行 stage + `企业级质量门禁` 并行 stage + `质量度量归档` stage。

## 4. 各企业级能力说明（面试题材）

### 4.1 性能测试（JD 点名 Locust；面经"关注哪些参数/瓶颈分析"）
- **关注指标**：吞吐（RPS）、响应时间分位数（P50/P95/P99，而非平均）、错误率、资源占用
- **门禁**：`run_perf_check.py` 解析 Locust 聚合统计，p95 与错误率不达标即非零退出
- **链路**：注册→登录→浏览/搜索→加购→下单→支付→查订单，每个虚拟用户独立账号（互不污染购物车）
- **瓶颈分析**：先定位 CPU 密集 / IO 等待 / 锁竞争 / 外部依赖；`ORDER_SIM_LATENCY` 放大下单竞态窗口

### 4.2 混沌工程 / 高可用（面经"如何模拟异常/支付失败原因"）
- **应用级**：`/api/chaos` 注入宕机(503)/随机错误(500)/延迟
- **网络级**：`mitmproxy_chaos_addon.py` 对支付接口注入 504（网关超时）
- **幂等正例验证**：弱网支付超时客户端重试（同 Idempotency-Key）→ 返回同一订单、库存只扣一次、不重复扣款——证明 BUG-003 已被幂等令牌修复

### 4.3 交易一致性（并发竞态，测开加分项）
- **防超卖**：`UPDATE products SET stock=stock-qty WHERE stock>=qty` 原子扣减，`test_integration.py` 用 12 线程并发下单断言"成交数 ≤ 库存、库存不穿底"
- **防优惠券重复核销**：`WHERE used==False` 条件更新 + 影响行数判断，并发只有一个请求核销成功
- **防购物车重复提交**：原子清空购物车按影响行数判断，第二个并发请求回滚

### 4.4 安全测试
- 越权（访问他人订单/地址）、伪造 token、SQL 注入（参数化查询）、弱口令、暴力破解限流、敏感字段不泄露

### 4.5 测试数据管理 / 造数（面经"数据污染/造数工具局限性"）
- **合成数据优先于脱敏生产数据**：合规、可重复、可版本化（`data_factory.py`）
- **隔离**：每用例 `reset_db()` 重建 + 数据工厂唯一命名空间，双重防污染

### 4.6 契约测试（面经"依赖第三方接口如何处理"）
- 抓包生成 HAR → 提取各路由响应字段 schema → 存 baseline → 每次 diff；删除字段/类型变化 = 破坏性变更（退出码非 0）

### 4.7 可观测性 / 质量度量
- `server.py` 暴露 `/metrics`：请求总量、5xx 错误数、平均/最大时延；与 Prometheus/Grafana 对接即质量仪表盘

## 6. 面试话术（如何讲这个项目对标字节）

- **"你的自动化框架怎么做的？"** → 四层金字塔 + 用例级隔离（reset_db + 数据工厂命名空间），不是堆脚本，是有质量门禁的体系
- **"性能测试关注哪些参数？"** → RPS/P95/P99/错误率，门禁卡 p95 与错误率，按加压拐点做容量规划
- **"如何模拟异常？"** → 应用级 /api/chaos + 网络级 mitmproxy 504，并验证幂等重试不重复扣款
- **"数据污染怎么解决？"** → 每用例重建 DB + 合成数据工厂独立命名空间
- **"最值得的 Bug？"** → BUG-003 弱网重复下单，用幂等令牌修复；并新增并发防超卖/防重复核销的竞态防护
- **"为什么造这个体系？"** → 把"会写用例"升级为"质量赋能"：功能/性能/安全/混沌/契约全部自动化且进 CI，fail fast
