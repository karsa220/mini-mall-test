# 缺陷报告

> 本项目预埋的 3 个典型缺陷，用于演示"测试发现缺陷"的能力。每条缺陷都关联到需求条款、用例编号、复现步骤和证据来源。

## BUG-001：购物车加购数量未做下限校验

| 字段 | 内容 |
|---|---|
| 缺陷编号 | BUG-001 |
| 标题 | 加购数量 0 或负数未被服务端拒绝 |
| 模块 | 购物车 |
| 严重级别 | 一般（数据不破坏业务，但脏数据） |
| 优先级 | P1 |
| 状态 | 已确认，修复中 |
| 关联需求 | FR-301 "数量必须为正整数" |
| 关联用例 | CART-04、CART-05 |
| 发现方式 | 手工 + 接口自动化（pytest xfail） |
| 报告人 | 本人 |
| 报告时间 | 2026-09-06 |

**前置条件**：已登录（任意有效账号）

**复现步骤**：
```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:5000/api/login -H "Content-Type: application/json" \
  -d '{"username":"test01","password":"123456"}' | python -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")

# quantity = 0，应被拒绝，实际成功
curl -X POST http://127.0.0.1:5000/api/cart/add -H "Authorization: $TOKEN" \
  -H "Content-Type: application/json" -d '{"product_id":3,"quantity":0}'
# 返回 code=0（成功），实际应为 2002

# quantity = -1，应被拒绝，实际成功
curl -X POST http://127.0.0.1:5000/api/cart/add -H "Authorization: $TOKEN" \
  -H "Content-Type: application/json" -d '{"product_id":3,"quantity":-1}'
# 返回 code=0
```

**预期结果**：`code=2002, msg="quantity 必须为正整数"`

**实际结果**：`code=0, msg="加购成功"`，购物车出现 quantity=0/-1 的脏数据，后续下单金额计算异常

**根因定位**：`app/server.py` 的 `/api/cart/add` 只校验了 `quantity > 库存`，未校验 `quantity >= 1`

**修复建议**：
```python
if qty < 1:
    return resp(2002, "quantity 必须为正整数")
```

## BUG-002：优惠券门槛判断少了边界值（评审疑问命中）

| 字段 | 内容 |
|---|---|
| 缺陷编号 | BUG-002 |
| 标题 | 订单金额恰好等于门槛时无法使用优惠券 |
| 模块 | 下单/优惠券 |
| 严重级别 | 严重（影响所有"凑单到门槛"的营销场景） |
| 优先级 | P0 |
| 状态 | 已确认 |
| 关联需求 | FR-402 "满 30.00 元减 10.00 元（含 30.00 整）" |
| 关联用例 | CP-01 |
| 发现方式 | 需求评审时主动提出"门槛边界值"问题 → 提测后用 CP-01 复现 |

**复现步骤**：
```bash
# 1. 登录
TOKEN=...

# 2. 加购 1 件显示器支架（30.00 元）
curl -X POST http://127.0.0.1:5000/api/cart/add -H "Authorization: $TOKEN" \
  -H "Content-Type: application/json" -d '{"product_id":3,"quantity":1}'

# 3. 下单并用券
curl -X POST http://127.0.0.1:5000/api/order/create -H "Authorization: $TOKEN" \
  -H "Content-Type: application/json" -d '{"coupon_code":"MAN30JIAN10"}'
# 返回 code=3002 "未达到优惠券使用门槛"
```

**预期结果**：`code=0`, `discount=10.00`, `payable=20.00`（需求明确"含 30.00 整"）

**实际结果**：`code=3002, msg="未达到优惠券使用门槛"`

**根因**：`app/server.py` 的 `calc_amount` 写了 `if total > coupon["threshold"]`（严格大于），应为 `>=`

**修复建议**：
```python
if total >= coupon["threshold"]:
    discount = coupon["discount"]
```

**评审批注**：本缺陷是需求评审环节（FR-402）我主动追问"恰好 30.00 整能不能用券"后命中。**说明早期介入评审的风险识别能直接转化为发现缺陷的能力**。

## BUG-003：下单接口无幂等控制（弱网下必现，Repeat Advanced 复现）

| 字段 | 内容 |
|---|---|
| 缺陷编号 | BUG-003 |
| 标题 | 同一购物车重复提交会产生多笔订单 |
| 模块 | 下单 |
| 严重级别 | 严重（弱网下必现，导致用户实际支付 > 应付） |
| 优先级 | P0 |
| 状态 | 已确认 |
| 关联需求 | FR-403 "防重" |
| 关联用例 | ORD-04、NET-03 |
| 发现方式 | 需求评审提出 + 自动化 xfail + Charles Repeat Advanced 5 并发复现 |

**复现步骤**：
```bash
# 准备：登录 + 加购商品 2 数量 1
TOKEN=...

# 同一会话连续发两次下单请求（模拟双击/重试）
curl -X POST http://127.0.0.1:5000/api/order/create -H "Authorization: $TOKEN" \
  -H "Content-Type: application/json" -d '{}'
curl -X POST http://127.0.0.1:5000/api/order/create -H "Authorization: $TOKEN" \
  -H "Content-Type: application/json" -d '{}'
# 返回两个 order_id 不同的订单，金额相同
```

**用 Charles Repeat Advanced 复现（最权威证据）**：
1. 抓一条 `POST /api/order/create` 请求
2. 右键 → Repeat Advanced → Iterations=5, Concurrency=5
3. 查询 `/api/orders`，data 数组长度=5（预期 1）

**预期结果**：重复请求只生成 1 笔订单（幂等）

**实际结果**：每发一次生成 1 笔，5 次生成 5 笔

**根因**：`app/server.py` 的 `/api/order/create` 未携带 `client_request_id` 等幂等键，服务端也未做幂等缓存

**修复建议**（任一）：
1. 客户端生成请求唯一 ID，服务端用 Redis 缓存 ID → 30 秒内同 ID 直接返回首次结果
2. 服务端在事务内"校验购物车状态 + 创建订单 + 清空购物车"必须原子化（基于购物车快照建锁）

**业务影响**：弱网下客户端超时重试直接触发，本质等价于用户被多扣款。
